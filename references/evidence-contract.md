# 证据与引用契约

这是所有场景共用的 Evidence Gate。目标不是“多放链接”，而是让每个会改变选择的结论都能追溯、分级并知道边界。

## 1. 先拆主张

把回答拆成最小可核验主张：资格、当前价格、费用、时限、权利义务、风险、体验。一个引用只支持它真正覆盖的主张，不用首页链接替代具体条款页。

## 2. 状态定义

| 状态 | 何时使用 | 能否进入排名 |
|---|---|---|
| 官方直接确认 | 政府、学校、合同/条款、银行或服务商官方页面直接支持 | 可以 |
| 第一方自述 | 商家/产品自己陈述，尚无独立确认 | 可以，但必须标明局限 |
| 第三方支持 | 成熟平台或多个可追溯用户经验支持 | 仅用于体验、口碑或初筛 |
| 合理推测 | 间接证据推断，申请/签约前必须确认 | 不可作为硬资格依据 |
| 无法验证 | 无可靠或直接证据 | 不可以 |

## 3. 风险门槛

- 高风险：身份、税务、法律、医疗急症、保险保障、信用申请资格、签约和大额付款。必须有直接适用的官方来源；否则只写“待确认”，并给出确认对象和问题。
- 中风险：价格、库存、退款、费用、预约、交通、营业时间。优先第一方并标注核验日期；聚合平台只能辅助。
- 低风险：主观体验、口味、噪音、社群气氛。可综合近期第三方和社区信息，但要区分事实与意见。

## 4. 冲突处理

1. 比较发布日期、适用地区、身份、产品版本和生效日期。
2. 具体条款优先于营销页，当前规则优先于旧文章，直接主管机构优先于转述。
3. 官方来源互相冲突时，不自行“选一个顺眼的”；并列写明冲突，说明哪个机构有最终决定权，并给用户可复制的确认问题。
4. 用户经验与官方规则冲突时，规则用于资格/义务，经验仅用于执行风险。

## 5. 推荐约束

每个正式推荐至少要有：

- 为什么满足用户硬约束；
- 资格依据或适用条件；
- all-in 成本或无法计算的缺口；
- 关键风险与可逆性；
- 直接来源和核验日期。

在信用卡等审批场景中严格分开：

- **能申请**：官方申请资格明确覆盖用户情况。
- **可能获批**：只能根据 pre-qualification、已有关系或有限数据估计，不保证。
- **值得申请**：收益、费用、hard pull、后续路径符合用户目标。

## 6. 输出模板

```text
核验日期：YYYY-MM-DD
假设：……

结论：……
证据状态：官方直接确认 / 第一方自述 / 第三方支持 / 合理推测
适用条件：……
来源：支持具体主张的直接链接

未验证：……（不进入排名）
下一步：……
Human gate：提交/付款/签字前请确认……
```

## 7. 机器校验

正式比较可把证据写成 JSON，运行 `python scripts/validate_evidence.py evidence.json`。高风险主张缺官方来源、推荐引用未验证主张、缺核验日期时应失败。
